# ## Subject ##
#
# <type>: <subject>
#
# The type is one of these, and no other (there are no scopes):
#
#   feat = Create a capability e.g. a package, profile, option, command
#     or file of an image.
#   feat! = Change a capability that users rely on, in a way that
#     breaks them.
#   fix = Fix an issue e.g. bug, typo, accident, misstatement, or an
#     insecure package.
#   perf = A change that MUST be just about performance.
#   refactor = A change that MUST be just a refactoring.
#   drop = Delete a capability that nothing relies on e.g. feature,
#     option, package, platform.
#   drop! = Delete a capability that users rely on.
#   docs = A change that MUST be only in the documentation or comments.
#   style = A change that MUST be just about format or looks.
#   test = Add or change tests.
#   build = Change the build process, or tools, or infrastructure.
#   ci = Change the continuous integration workflows.
#   chore = Any other upkeep, e.g. bump a dependency that has no
#     vulnerability.
#   conf = Change the configuration of Claude or of another tool.
#
# Start the subject with a lowercase imperative present active verb,
# e.g. add foo. Wrong: adds foo, added foo, adding foo, foo added.
#
# Keep the summary within 72 characters.
#
# Do not use a sentence-ending period, unless it ends an abbreviation,
# e.g. feat: add feature for U.S.A.
#
# Do not put other meta-information in the summary: no [bug], (release),
# #12345 or JIRA-666. Pass a ticket ID as a trailer instead,
# e.g. Issue: 25.
#
# ## SemVer ##
#
# The type of the summary sets the version bump:
#
#   feat!, drop! = MAJOR, when there is an incompatibility.
#   feat = MINOR, when there is a new capability.
#   fix, perf, refactor = PATCH.
#   Any other type = no bump.
#
# Use drop! only when what goes was relied upon. Use drop instead when
# nothing relies on it.
#
# ## Body ##
#
# Add a blank line after the summary line.
#
# Use 72 characters maximum per line for typical word wrap text, and as
# many as needed for atypical text, such as URLs, terminal output and
# formatted messages.
#
# Use Markdown: links for external references, e.g.
# [text](https://example.com), code blocks for terminal output, lists
# for enumerating changes, and headings for long messages.
#
# ## Trailers ##
#
# Trailers suitable for tracking and also for `git interpret-trailers`,
# one per line, in the style of email headers:
#
#     Keywords: security, encryption, authentication
#     Importance: high
#     References: ...
#     Supersedes: ...
#     Obsoletes: ...
#     See-Also: ...
#
# "Importance: high" gives the commit priority for code review and for
# testing on the continuous integration server. "Supersedes",
# "References" and "Obsoletes" help look up earlier commits or URLs.
#
# Example of "See-Also:" trailers that mean "see this additional
# information" and links to relevant web pages, issue trackers, blog
# posts, etc.:
#
#     See-Also: https://example.com/
#     See-Also: Issue #123 <https://example.com/issue/123>
#
# Example of "Co-authored-by:" trailers that list each author's name
# and their preferred commit message email address or contact URL:
#
#     Co-authored-by: Alice Adams <alice@example.com>
#     Co-authored-by: Bob Brown <https://bob.example.com>
#
# We like to use the "Co-authored-by:" trailers when we pair program,
# triple program, and group program. These are parsed automatically by
# some version control services (e.g. GitHub, GitLab) and will link
# to the authors' accounts and show up on the authors' commit history.
#
# The Git tools require trailers to be last in a commit message,
# and must be one trailer per line, and with no extra lines between.
#
# ## Usage ##
#
# Configure git to use the template file by running:
#
#     git config commit.template docs/commit-template.txt
#
# This template intends for the commit to strip the comments.
# To strip the comments, your git `commit.cleanup` config must be `strip`.
#
